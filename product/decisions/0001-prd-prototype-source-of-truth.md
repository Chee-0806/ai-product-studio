# 0001 PRD 与原型各自持有一种真相

- 日期：2026-11-11
- 状态：accepted
- 关联需求：全部

## 背景

AI 协作里最常见的事故不是「写得慢」，而是同一件事有两份说法：

- PRD 说按钮叫「开始录音」，原型写「立即录音」；
- PRD 标了 4 条已出原型，实际只有 3 页；
- 原型里加了一个没人评审过的设置项，PRD 完全不知道。

一旦出现两个版本，agent 会挑一个继续做，而且做得很快。

## 决策

按真相类型拆权，不追求「一个文件装下所有东西」：

| 真相 | 权威 | 校验方式 |
| --- | --- | --- |
| 要做什么、验收 | `product/PRD.md` | REQ ID、状态、验收的格式校验 |
| 界面与交互 | `prototype/screens/*.html` | 页面 meta、`data-req` 反向追溯 |
| 覆盖进度 | 不单独存 | 由 `data-req` 自动推导 |
| 为什么这样取舍 | `product/decisions/` | 只增不改，PRD 链接 |

强制规则：

1. 原型里的每个需求实现必须带 `data-req`，且该 REQ 必须已存在于 PRD。
2. 每条非 `dropped` 需求的状态必须与页面覆盖一致：`prototyped` 必须有页面，`dropped` 不得有页面。
3. PRD 与原型在**同一次变更**里更新，版本号同步。
4. 覆盖关系不手工维护，由 `scripts/sync.mjs` 生成目录页。

## 备选方案

- **单一 `spec.yaml` 作为唯一源，PRD 由它生成**：机器友好，但产品经理无法直接改 PRD，评审体验差。
- **PRD 生成原型**：适合标准化页面，不适合探索式设计；生成结果仍需人工改，改完照样漂移。
- **原型反推 PRD**：会鼓励「先做后补」，需求与验收永远滞后。
- **人工维护「需求 ↔ 页面」表格**：表格本身会成为第三份真相，没人愿意同步。

## 代价与影响

- 语义一致性（文案、边界态是否真的符合验收）无法完全自动校验，依赖评审清单与 agent 契约，必须诚实承认。
- `data-req` 需要人工标注；标错时校验只能发现「指向不存在的 REQ」，发现不了「标在了错误的位置」。
- 目录页是生成物，不能手改；改页面后需要跑 `npm run sync`。
