# 工作流

> 本文给 AI 和维护者看。产品经理只需要双击 `工作台.html`：上面有当前阶段、下一步、需求进度和原型页面。

## 1. 五个阶段

| 阶段 | 你要回答的问题 | 产物 | 离开条件 |
| --- | --- | --- | --- |
| discovery | 值得做吗？证据是什么？ | `product/discovery/*.md` | 证据支持一个明确方向 |
| prd | 做什么？怎样算完成？ | `product/PRD.md` 的 REQ 块 | 每条需求有 ID、优先级、验收 |
| prototype | 界面如何承载这些需求？ | `prototype/screens/*.html` | 主流程能点通，需求有 `data-req` |
| review | 有没有漏、有没有多、文案是否一致？ | 评审结论 + 修改 | 人明确说「通过」 |
| handoff | 研发能否据此拆任务？ | 分享链接 / 导出物 | 研发确认可以开工 |

阶段可以回退。原型阶段发现需求本身有问题，回 PRD 改，不要在原型里打补丁。

## 2. 两种工作模式

### 探索模式

- 产物只放 `prototype/spikes/`，可以不完整、可以死链。
- 不写 `data-req`，不进入工作台，不要求通过校验。
- 一旦决定采纳：先在 PRD 建 REQ 与验收，再落到 `screens/`，最后删除或标注 spike。
- 不允许把 spike 直接改名为正式页面。

### 正式变更

任何会影响已存在需求或页面的改动，按 `AGENTS.md` 第 6 节的顺序一次做完：

1. 搜索受影响的 `REQ-` 与 `data-req`；
2. 改 PRD（行为、验收、版本、变更记录）；
3. 改原型；
4. 必要时新增 ADR；
5. 更新 `STATE.md`；
6. `npm run check`；
7. 按格式汇报。

## 3. 每次会话怎么开

agent 的开场动作固定：

1. 读 `AGENTS.md`、`STATE.md`、`product/PRD.md` 的相关部分；
2. 用一句话说明：当前阶段 + 本次要改的 REQ/页面 + 是否与 PRD 冲突；
3. 在范围内直接做，不反复确认。

可以直接复制这段提示词：

```text
先读 AGENTS.md、STATE.md、product/PRD.md。
用一句话告诉我：当前阶段、下一步、你准备改哪些 REQ 和页面。
如果我的要求和 PRD 冲突，先指出冲突，不要直接改需求。
然后开始做，结束时按 AGENTS.md 第 8 节汇报，并跑 npm run check。
```

## 4. 常用提示词

### 新增需求

```text
在 product/PRD.md 新增一条 REQ-00x，先只写状态 draft、优先级、用户故事、行为与验收，不要动原型。
写完升 minor 版本、补变更记录，并告诉我这条需求会影响哪些页面。
```

### 改界面

```text
只处理 REQ-00x 的界面。先列出所有带 data-req="REQ-00x" 的页面和元素，再改。
文案必须与 PRD 中「」标注的内容逐字一致；改文案时两处同改。
完成后更新 STATE.md 并跑 npm run check。
```

### 评审

```text
按 docs/review-checklist.md 评审 REQ-001 ~ REQ-004。
不要改文件，先输出：必改项、建议项、PRD 与原型不一致处、无法验证的边界。
```

### 修复一致性

```text
运行 npm run check，逐条修复错误。不要通过删需求、删页面或跳过校验来让检查变绿。
修完解释每个错误的原因。
```

### 交接

```text
把当前 PRD 里 approved 的需求整理成研发可执行的清单：REQ ID、行为、验收、原型链接、未决问题。
不要新增需求，不要改状态。
```

## 5. 版本与状态

版本遵循 SemVer，只存在于 `product/PRD.md`：

- patch：澄清文案/验收，行为不变；
- minor：新增/删除需求、流程或结构变化；
- major：产品方向或核心流程重做。

需求状态：

```text
draft ──► prototyped ──► approved ──► delivered
  │            │
  └────────────┴──────► dropped
```

- `approved` / `delivered` 只能由人确认后设置。
- `dropped` 保留 ID 与放弃原因，不删除历史。

## 6. 交接与归档

评审通过后：

- 工作台链接直接发给参会人；
- 需要文档时从 PRD 导出，不另写一份「精简版需求」（会变成第二份真相）；
- `prototype/spikes/` 里未被采纳的探索，在阶段结束时删除或移到归档分支；
- 新决策追加 ADR，旧 ADR 标记 `superseded by`。

## 7. 反模式

- 先做原型再补 PRD，且不补验收；
- 为「看起来完整」把 `draft` 改成 `prototyped`；
- 在原型里加 PRD 没有的入口或设置项；
- 手工维护「需求 ↔ 页面」表格；
- 直接改 `工作台.html`；
- 一次性重写整个 PRD，导致无法判断哪条需求变了；
- 用「基本完成」「应该没问题」代替 `npm run check` 的结果。
