# 需求发现与澄清

## 什么时候用

- 用户说「我想做一个……」「帮我看看这个需求」。
- 手上只有访谈记录、聊天记录、竞品截图，没有明确问题。
- PRD 还空着，或现有需求明显是「功能清单」而不是「问题」。

## 输入

- 用户的原话、材料、约束（时间、预算、团队）。
- `STATE.md`：当前阶段与目标。
- 已有的 `product/discovery/*.md` 和 `product/PRD.md`（如果有）。

## 步骤

1. **复述**：用一句话说清「谁、在什么场景、遇到什么问题、现在怎么解决」。不确定的地方标出来。
2. **先问最关键的问题**：按优先级问 5 个，最多 10 个，不要一次抛 20 个。覆盖：
   - 业务目标与成功标准；
   - 目标用户与非目标用户；
   - 当前替代方案与真实痛点；
   - 主流程与异常流程；
   - 权限、数据、隐私、合规；
   - 一期范围与明确不做；
   - 依赖、风险、上线时间。
3. **完整度评分**：按 100 分评估上述维度，列出最影响后续的 5 个缺口。
4. **写问题定义**：`product/discovery/NNN-problem-brief.md`，包含问题、证据、用户、假设、不解决什么、下一步。
5. **给方向**：最多 3 个方案，说明推荐哪个、为什么、代价是什么。不要直接写功能清单。
6. 用户确认方向后，交给 `scope` 或 `prd` 技能。

## 输出

```text
问题：……
证据：……（没有证据就写「假设」）
目标用户：……
建议方向：A / B / C，推荐 A，因为……
还需要确认：……
```

## 不要做

- 不要把「用户说想要 X」当成需求证据。
- 不要编造数据、访谈结论或竞品事实；不确定就标「待验证」。
- 不要在问题没定义清楚时直接写 PRD 或画原型。
- 不要一次问完所有问题；先问会改变方案的那几个。
