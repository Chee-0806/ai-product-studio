# PRD 写作与维护

## 什么时候用

- 方向已确认，要把讨论落成需求。
- 用户要改一条已有需求的范围、文案或验收。
- 需要检查 PRD 是否缺验收、状态是否虚报。

## 输入

- `AGENTS.md` 的硬规则。
- `product/PRD.md` 现有需求与版本。
- 相关 `product/decisions/*.md`。
- 用户确认过的范围与边界。

## 步骤

1. 读 PRD，找到下一个未使用的 `REQ-NNN`。**ID 永不复用**。
2. 按下面的格式新增或修改：

   ```md
   ### REQ-00x 一句话需求名

   - **状态**: draft
   - **优先级**: P0
   - **用户故事**: 作为……，我希望……，这样……
   - **行为**:
     1. ……
     2. ……
   - **验收**:
     - [ ] 可判断真假的条件
     - [ ] 边界或异常条件
   - **边界**: ……
   ```

3. 验收标准必须能判断真假；涉及界面文案时用「」标出，要求原型逐字一致。
4. 状态按实际填：没原型用 `draft`；有页面用 `prototyped`；人工评审通过才用 `approved`。
5. 行为或范围变化时升 `version`：
   - patch：只澄清措辞；
   - minor：新增/删除需求、流程变化；
   - major：方向或核心流程重做。
6. 在「变更记录」补一行，写清影响了哪些 REQ。
7. 更新 `STATE.md` 的版本与下一步。
8. 交给 `prototype` 或 `change` 技能同步页面，最后跑 `npm run sync && npm run check`。

## 输出

```text
新增/修改：REQ-00x ……
版本：0.x.y → 0.x.z
影响页面：……（没有就写「待做原型」）
还需要确认：……
```

## 不要做

- 不要写实现方案、接口字段、数据库设计。
- 不要把多个独立行为塞进一条 REQ；拆分或标清子项。
- 不要写「体验流畅」「尽量快」这种无法验收的标准。
- 不要在 PRD 里粘贴页面布局或截图；界面以原型为准。
- 不要删除旧需求；用 `dropped` + 原因保留。
