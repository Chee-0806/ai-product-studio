# 产品与一致性评审

## 什么时候用

- 用户说「帮我评审一下」「看看还缺什么」「PRD 和原型对得上吗」。
- 准备把需求标成 `approved` 之前。
- 交接研发前。

## 输入

- `docs/review-checklist.md`。
- `product/PRD.md` 与 `prototype/screens/*.html`。
- `STATE.md` 的当前阶段。

## 步骤

1. **先跑机器检查**：`npm run sync && npm run check`。有错误先修，不要带着错误评审。
2. **PRD 评审**：问题与证据、用户与场景、范围、REQ 完整性、验收可判断、边界态、指标、开放问题。
3. **原型评审**：主流程、页面 meta、`data-req` 位置、文案逐字一致、示例数据、空/错/权限态、死链、360px 布局。
4. **交叉检查**：状态与覆盖、版本与 STATE、变更记录、决策链接。
5. **分级输出**：
   - 必改（阻塞）：会导致错误实现或无法验收；
   - 建议（不阻塞）：体验或表达优化；
   - 无法验证：需要真实数据、真实设备或业务确认的项。
6. 用户确认要修时，再改文件；不要边评审边偷偷改。
7. 评审通过后，问用户是否要发给研发；要的话运行 `npm run export`，只发 `dist/<产品>-v<版本>.zip`，不要打包整个工作区。

## 输出

```text
评审对象：PRD v0.x.y / N 个页面
机器检查：通过 / 失败（列错误）

必改：
- ……

建议：
- ……

PRD 与原型不一致：
- ……

无法验证：
- ……

结论：通过 / 有条件通过 / 不通过
```

## 不要做

- 不要把「检查通过」当成「内容正确」；机器只保证结构和进度。
- 不要用「体验不好」当结论；指出具体页面、元素和期望。
- 不要自行把状态改成 `approved` 或 `delivered`；必须有人明确确认。
- 不要在评审输出里粘贴大段 HTML 或 PRD。
- 没有证据时不要断言用户会怎么想。
